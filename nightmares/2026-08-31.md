## 1. The failed step never cleans up after itself

### Incident timeline (fiction, future-dated)

- 2026-11-14 09:12 — A checkout flow wraps inventory reservation and payment capture in one transaction. Payment capture reserves a hold at the provider, then throws on a declined card.
- 2026-11-14 09:12 — The transaction reports a successful rollback. Inventory is released. The payment hold is not.
- 2026-11-21 10:40 — Finance reconciliation finds a week of orphaned payment holds. Every one traces back to a step that started, produced a side effect, and failed before completing.

Accepted by the user as satisfying the reproduction rule; a different-machine reproduction has not been performed.

### Failing test (fact)

- Test: `scenarios/firsttx/failed-step-compensation.test.ts` (sha256:e59c7f4e14452d18efd088ca2207e26b945ca6fbffc8072b3177d59368682495)
- Expectation basis: documentation — `packages/tx/README.md:148` states the failed step's own compensation runs first: "1. Execute undo3 (if step3 started)"
- Control: a failed step without compensation triggers reverse-order rollback of completed steps (`packages/tx/tests/transaction.test.ts:614-654` pattern) — passed
- Expected: `["step1-run", "step2-start", "step2-compensate", "step1-compensate"]`
- Actual: `["step1-run", "step2-start", "step1-compensate"]`
- Failure signature: oracle violation — the failed step's registered `compensate` is never invoked; only completed steps are compensated

### Relevant code path (fact)

- `packages/tx/src/transaction.ts:102` — `completedSteps` increments only after a step resolves successfully
- `packages/tx/src/transaction.ts:120` — the catch path calls `rollback(stepIndex, error)` with the failed step's index
- `packages/tx/src/transaction.ts:218` — the rollback loop starts at `completedSteps - 1`, so the failed step at `stepIndex` is excluded even when it registered a `compensate`

### Impact note (estimate)

Any consumer that registers `compensate` on a step whose side effects precede its failure point is reachable: the step starts, mutates external state, throws, and its own cleanup silently never runs while the transaction reports rollback success. The README is internally inconsistent — line 138 says "all completed steps are rolled back", while the example at line 148 promises "Execute undo3 (if step3 started)". The implementation follows line 138, so either the rollback loop must include the failed step or the documented example is wrong. Until one side is fixed, users who trusted the example leak exactly one uncompensated side effect per failed transaction.

## 2. The save that quietly un-saves itself

Module: packages/local-first (incident-seeded from PR #129)

### Incident timeline (fiction, future-dated)

- 2026-12-02 08:59 — The slow load completes and applies yesterday's row to the cache. The screen silently reverts to the old address. The agent, seeing the old value, assumes the save failed and re-enters it — or drives to the wrong address.

### Impact note (estimate)

The user's committed write visibly reverts on screen, which reads as data loss and invites double submission. The library already encodes the correct invariant for background refreshes; the initial-load path is the one writer that skips it.

## 4. The receipt that gets refunded anyway

Module: packages/tx (incident-seeded from PR #129)

### Incident timeline (fiction, future-dated)

- 2027-02-10 14:03 — A checkout handler starts a transaction: reserve inventory, then capture payment with a retry policy. A double-clicked confirm button triggers a code path that calls `tx.commit()` while the capture step is still awaiting the provider.
- 2027-02-10 14:03 — `commit()` resolves. The UI shows the order as confirmed and navigates away.
- 2027-02-10 14:04 — The in-flight capture exhausts its retries and fails. The transaction, already committed, rolls back anyway: the inventory reservation is compensated while the confirmation screen the user saw stands. The order exists for the user and for support, but not in stock.

### Reproduction (fact)

```bash
node scripts/run-scenario.mjs --scenario 'scenarios/firsttx/incident-seeded-2026-08-31/tx/incident-01.test.ts' --module packages/tx --timeout-ms 30000
```

Observed: failed 4/4 runs (3 consecutive recorded). Evidence: `evidence/2026-08-31/incident-seeded/batch-tx.json`

Third-party reproduction: an independent codex agent session on the same host ran the recorded command unchanged and observed the same failure signature once (2026-08-31, candidate-failure). Evidence: `evidence/2026-08-31/incident-seeded/independent-repro-codex.json`

### Failing test (fact)

- Test: `scenarios/firsttx/incident-seeded-2026-08-31/tx/incident-01.test.ts`
- Expectation basis: documentation — `packages/tx/README.md` "After commit": the transaction becomes immutable; `packages/tx/src/types.ts` `TxStatus` lifecycle where `committed` is terminal
- Expected: either `commit()` during a running step throws `TransactionStateError`, or once `commit()` resolves no compensation runs and the state stays `committed` (the oracle accepts both)
- Actual: `{ commitOutcome: "resolved", stepOutcome: "Retry exhausted for step-1", compensated: ["step-1"], stateAfter: "rolled-back" }`
- Failure signature: oracle violation — `expected [ 'step-1' ] to deeply equal []`; compensations execute after a successful commit and the state leaves `committed`

### Relevant code path (fact)

- `packages/tx/src/transaction.ts:138-143` — `commit()` checks `status` but not `isStepRunning`, so it accepts a commit mid-step and marks the transaction committed
- `packages/tx/src/transaction.ts:112-121` — the still-running step's failure unconditionally calls `rollback(stepIndex, error)`
- `packages/tx/src/transaction.ts:212` — `rollback` overwrites `committed` with `rolled-back` and compensates completed steps

### Impact note (estimate)

Requires calling `commit()` without awaiting the in-flight step, so it needs a caller-side race (double submission, parallel handlers) — less reachable than #2 and #3, but the broken promise is the library's strongest one: a resolved `commit()` is not final. Whichever fix direction is chosen (reject commit while a step runs, or make commit win), the current behavior violates the documented lifecycle either way.
