# v0.3 Data, Evaluation, and Publication Contract

## Purpose and status

This document is the normative contract for v0.3 inputs, trust enforcement, result axes, evidence, reproduction, minimization, publication, and validator behavior. v0.3 is in progress.

[V0.1-CONTRACT.md](V0.1-CONTRACT.md) remains the immutable historical contract for v0.1 and v0.2. This document does not retroactively change their results, evidence, three-run rule, runner, harness, or image tags.

## Target and scope

The target remains `joseph0926/firsttx` at revision `f624b09f148c3368a51807f48d3237db20cef9c6`, limited to the registered `packages/tx`, `packages/local-first`, and `packages/prepaint` modules.

v0.3 includes packed-package consumer evaluation, public action and invariant catalogs, data-only seed and spec schemas, trusted plan construction, registered fixtures, a fixed action interpreter, trusted invariant evaluation, a separate result channel, deterministic reduction, replay, the historical audit, and pre-registered engineering experiments.

The v0.3 Dockerfile and build context live under `docker-v0.3/`. The frozen v0.2 builder copies the entire `docker/` directory, so placing a v0.3 file there would change the legacy build input closure. The v0.3 harness likewise lives under `harness-v0.3/`.

Multi-repository support, a web application, automatic fixes or merges, production traffic, persistent synthetic customers, a shared runner package, TLA+ generation, and claims of proving correctness are excluded. Another physical host is not a completion gate. Adding `fast-check`, registering a schedule, adding a second repository, or deleting a published nightmare requires separate user approval.

## Product invariants

- A generator produces one data-only `NightmareSeed`, never executable test code.
- Generator output cannot assert provenance, choose a target revision, define an oracle, widen an execution policy, or modify product or evaluator code.
- Public findings use only declared package exports, registered public actions, and allowed environmental seams.
- An invariant comes from evidence independent of the generated scenario.
- Generated data, target stdout, target stderr, and ordinary product files cannot create a trusted verdict.
- Every evaluation uses an isolated container, no network, a command allow-list, time and resource limits, no secrets, and no Docker socket.
- Passing and unrunnable tests are never published as product bugs.
- Automation can create a digest candidate but cannot promote it to `nightmares/`.
- v0.2 runtime inputs and historical outputs remain frozen under `history/` manifests.

The rationale for the data-only boundary is recorded in [ADR 0001](adr/0001-data-only-evaluation-boundary.md).

## Trust enforcement

The generator environment receives read-only source, public catalog identifiers, and contract documents. Its only accepted output is one schema-valid seed.

The trusted host owns target registration, revision lookup, invariant provenance, fixture lookup, operator transformation, canonical validation, digest creation, plan construction, budgets, and policy.

The evaluator container receives a clean pinned product artifact, registered fixtures, the fixed interpreter, the trusted invariant evaluator, and a dedicated result path or IPC channel. The host validates the result schema and digest after the container exits. Missing or malformed trusted results, early exit, timeout, resource exhaustion, and log truncation are not candidate failures.

Raw stdout and stderr are retained only as untrusted evidence. Marker-shaped seed values or product logs cannot affect classification. A malicious target package intentionally impersonating the dedicated result channel is outside the v0.3 threat model.

## Public reachability

A `public-export` result must satisfy all of the following:

- The target and every first-party workspace dependency are built and packed as digest-pinned tarballs.
- A clean temporary consumer installs only those tarballs and pinned third-party dependencies.
- The consumer lockfile has no workspace protocol, workspace symlink, source mount, or registry substitution for a first-party package.
- The evaluator imports the real package name through its root or an explicitly registered exported subpath.
- Product state is created through registered public actions.
- A test seam controls only environment behavior such as time, an external response, storage failure, or completion order.

Private source imports, private class construction, private state mutation, and internal state-machine bypasses are forbidden. A valuable result that fails the public boundary may be retained as an `internal-contract-finding` but cannot be a confirmed public counterexample.

Phase 1 owns `registrations/v0.3/packages.json`, `registrations/v0.3/consumer-lock.yaml`, `history/v0.3-public-boundary.json`, and `evidence/v0.3/phase1-contracts.json`. The registration pins the target revision, package manager, first-party package manifests, declared import specifiers, build and pack arguments, exact clean-consumer dependencies, and the complete consumer lockfile. Every direct and transitive first-party resolution is overridden to its registered tarball. The Docker build copies the registered lockfile and installs with `--frozen-lockfile`; it never resolves or rewrites the lockfile while creating evidence.

The evidence receipt is produced by `node scripts/prepare-v03-contracts.mjs --target <firsttx path>` from `docker-v0.3/` and `harness-v0.3/`. It records four packed tarballs, their digests and manifests, the frozen consumer lockfile, real Node import results, forbidden-import results, target-relative first-party realpaths, and historical public traces. The lockfile may contain a first-party package only as the registered `file:` tarball entry, and each target package must resolve every first-party dependency to that tarball entry. The final consumer image contains no target source tree.

The receipt verifies each registered `sourceManifestSha256` against the package manifest bytes in the pinned-revision archive and records the verified digests; a mismatch fails the preparation. The receipt also hashes the preparation runner and records the normalized Docker run arguments used for the probe. The probe observes the read-only root, target source absence, Docker socket absence, effective capability mask, no-new-privileges state, process limit, memory limit, CPU quota, and loopback-only assigned network interfaces from inside the container. A claimed isolation property without its matching runner digest, argument, and supported observation is invalid.

Each Phase 1 historical reachability wrapper has `status: provisional` and one existing reachability value: `public-export`, `internal-contract`, or `unreachable`. `unreviewed` is not a Phase 1 exit result. A provisional `public-export` requires a successful packed-consumer public trace whose action list and observed defect behavior exactly match the audit expectation. A provisional `internal-contract` requires the relevant private import to be rejected by that consumer and identifies the missing public action. Phase 1 does not change the historical scenario, evidence, human verdict, or publication state.

`contracts` validates the strict registration, frozen lockfile, complete seven-item provisional audit, hashed integration receipt, tarball-only first-party resolutions, exact export agreement, allowed public imports, forbidden private imports, module-bound audit pointers, public traces, runner-bound isolation evidence, and owned negative fixtures. It does not rebuild the target. Rebuilding the receipt is the explicit preparation command above and must use the pinned target revision.

## Oracle contract

Allowed source kinds are requirements or documentation, existing tests, public types and contracts, fixed-version comparisons, reference implementations, differential relations, and metamorphic relations. Implementation source alone can guide generation but cannot authorize a public oracle.

Each invariant registration records `sourceKind`, `sourceRef`, `sourceCommit`, `authoredBeforeGeneration`, `visibility`, `strength`, and `corroboratingRefs`. Strength is one of `normative`, `corroborating`, `inferred`, or `implementation-only`.

A public finding requires one normative source or at least two independent corroborating sources. A generator cannot add an invariant or assert that it predates generation. A known patched defect must pass the per-patch F-to-P check: fail on the defect artifact and pass when only that defect patch is removed.

## NightmareSeed

Required fields are `schemaVersion`, `catalogVersion`, `id`, `invariantId`, `actors`, and `actions`. Each action names a registered action, actor, arguments, and optional binding use or declaration.

The v1 seed schema is `bug-dreamer/nightmare-seed/v1`. `actors` is a non-empty array of unique lower-case identifiers. `system`, `host`, `evaluator`, `target`, `result`, and identifiers beginning with `__` are reserved. Each action has exactly `actionId`, `actor`, `arguments`, and `bind`. A binding declaration is `{ "name": <id>, "type": <registered type> }`; no declaration is represented by `null`. An argument binding reference is the single-field object `{ "$binding": <name> }`. References resolve only to an earlier declaration and must match the action registration's required type.

The seed rejects empty actor or action collections, duplicate or reserved actors, unknown actions or invariants, invalid arguments, duplicate bindings, forward references, missing bindings, binding type mismatches, imports, source paths, function bodies, shell commands, arbitrary assertions, provenance claims, target revisions, package names, export entries, run counts, and resource policy. Seed and spec acceptance also require at least one `tx.run` action whose final occurrence declares the outcome matching the invariant's normalized observed kind; an inapplicable invariant pairing is `rejected-policy` rather than a downstream infrastructure error. Integer action arguments must be non-negative safe integers (`rejected-schema` otherwise), and the Phase 2 action policy limits `tx.start` `timeoutMs` to 10000 ms, retry `maxAttempts` to 5, and retry `delayMs` to 1000 ms so that the worst-case scripted wait stays bounded well under the evaluation budget; exceeding a policy limit is `rejected-policy`.

Values such as `0`, an empty string, `false`, and an empty collection remain valid when the registered argument schema allows them.

## NightmareSpec and ExecutionPlan

A trusted transformer combines a canonical seed with target, invariant, fixture, action, and operator registrations to create a self-contained `NightmareSpec`. The spec includes:

- `schemaVersion`, `seedDigest`, `targetRegistrationId`, and `invariantRegistrationId`
- actors and complete base and transformed actions
- a stable `instanceId` for every action
- all arguments and bindings needed for replay
- trusted transformation records with catalog, before, and after digests
- schedule controls that refer to action instance IDs
- complete registered fixture materialization records

Environment fixture kinds are limited to `public-current-version`, `public-previous-version`, `public-test-seam`, `documented-wire-state`, and `external-environment`. Each fixture records its registration and digest, producer artifact, public action trace or canonical wire payload, materializer, state digest, and consumer. The materializer verifies the producer artifact and resulting state digest before execution.

The trusted plan builder converts a validated spec into `ExecutionPlan` data containing resolved action instances, bindings, fixture setup, virtual time, and schedule controls. The interpreter looks up every action in the registered catalog and revalidates its arguments. It never executes nightmare-specific TypeScript, imports, or assertions.

Phase 2 owns `registrations/v0.3/phase2-catalog.json`, `contracts/v0.3/spec-cases.json`, the referenced seed corpus, `evidence/v0.3/phase2-spec.json`, and `evidence/v0.3/phase2-trust.json`. The catalog is a minimal vertical slice over the already verified `@firsttx/tx` public export. It registers `tx.start`, `tx.run`, and `tx.commit`, two independent public invariants, and one `public-test-seam` fixture. Expanding the adopted pipeline to every registered module remains Phase 5 work.

Phase 2 permits only the identity transformation: base and transformed actions are byte-equivalent after canonicalization, and transformation and schedule-control arrays are empty. Phase 3 owns non-empty operator transformations and schedule controls.

`node scripts/prepare-v03-spec.mjs` deterministically rebuilds the checked-in seed, spec, and plan evidence. `node scripts/prepare-v03-trust.mjs --target <firsttx path>` verifies the pinned target and recorded Phase 1 consumer image, builds `docker-v0.3/Dockerfile.trust`, runs the registered trust cases under the fixed isolation policy, and replaces only `evidence/v0.3/phase2-trust.json`. The evaluator image extends the recorded clean packed-package consumer and imports `@firsttx/tx` by package name. The production evaluator entrypoint contains no negative-case branches; the registered negative trust modes run through a separate case-only entrypoint selected by the recorded container command, and each case's command is part of the trust evidence.

## Canonical wire format

- The wire format is UTF-8 JSON canonicalized with RFC 8785 JCS.
- JCS serialization is provided by the exact-pinned `canonicalize@4.0.0` package. A separate raw parser performs fatal UTF-8 decoding, duplicate-key detection, Unicode validation, lexical negative-zero rejection, and resource-limit enforcement before canonicalization.
- Duplicate keys, invalid Unicode, `NaN`, `Infinity`, and unknown fields are rejected.
- Version 1 limits are 256 KiB input, 16 actors, 64 actions, 16 fixtures, 128 schedule controls, nesting depth 16, 8 KiB per string, and 128 entries per general collection.
- A limit change requires a schema-version and benchmark-registration change.
- Digests use SHA-256 with an artifact and schema domain prefix.

The v1 spec digest is SHA-256 over the bytes `bug-dreamer/nightmare-spec/v1\0` followed by canonical JSON bytes. Evidence records the canonicalizer version and digest. YAML is documentation only and is never accepted as executable input.

## Result axes

Every audit record contains every axis. A wrapper with `status: unassessed` and `value: null` represents an audit not yet run without adding `unassessed` to a result enum.

| Axis | Values |
| --- | --- |
| spec acceptance | `accepted`, `rejected-schema`, `rejected-catalog`, `rejected-policy` |
| plan | `planned`, `planner-error`, `not-run` |
| evaluator | `evaluated`, `evaluator-error`, `not-run` |
| batch | `completed`, `budget-exhausted`, `not-run` |
| execution | `pass`, `candidate-failure`, `unrunnable`, `not-run` |
| repeat reproduction | `consistent`, `intermittent`, `diverging-signature`, `incomplete`, `not-run` |
| independent reproduction | `matched`, `diverging-signature`, `diverging-build`, `unrunnable`, `not-run` |
| reachability | `public-export`, `internal-contract`, `unreachable`, `unreviewed` |
| oracle | `independent`, `disputed`, `implementation-only`, `missing` |
| minimization | `one-minimal`, `reduced-not-one-minimal`, `not-reduced`, `not-applicable` |
| human verdict | `real-bug-worth-fixing`, `real-bug-not-worth-fixing`, `wrong-expectation`, `undecided` |
| publication | `digest-candidate`, `confirmed-counterexample`, `internal-contract-finding`, `legacy`, `rejected`, `duplicate` |

An unrunnable result has kind `infrastructure` or `test-definition`. A trusted wrapper, evaluator, or serializer failure is `evaluator-error` plus `unrunnable: infrastructure`, not a seed or test-definition failure.

### Axis compatibility

Rules are applied from top to bottom.

| Preceding state | Required downstream state |
| --- | --- |
| spec is `rejected-*` | plan, evaluator, batch, execution, repeat, and independent reproduction are `not-run` |
| plan is `planner-error` | evaluator, batch, execution, repeat, and independent reproduction are `not-run` |
| evaluator is `evaluator-error` | execution is `unrunnable: infrastructure`; repeat and independent reproduction are `not-run` |
| batch budget is exhausted before an item starts | evaluator, execution, repeat, and independent reproduction are `not-run` |
| budget is exhausted after one to four matching candidate failures | repeat is `incomplete`; independent reproduction is `not-run` |
| execution is `pass` or `unrunnable` | repeat and independent reproduction are `not-run`; publication cannot be confirmed |
| execution is `candidate-failure` | a schema-valid violation identity is required before later gates run |

Every `not-run` records `blockedByAxis` and `blockedByState`. `incomplete` records every attempt and the batch budget blocker. A pass-and-failure mixture is `intermittent`; different candidate signatures are `diverging-signature`; otherwise one to four matching candidate failures are `incomplete`.

## Failure identity and evidence

A candidate-failure requires `invariantRegistrationId`, `normalizedObservedKind`, allow-listed normalized observed fields, and `targetArtifactDigest`. `observedKind` records the actual observation from the registered observation universe (`returned-value`, `thrown-error`), and observed fields are validated against the actual kind's registered schema. An observation whose kind differs from the invariant's expected kind is therefore a well-formed candidate-failure, while a passing result must observe the expected kind. A missing, malformed, or field-incomplete trusted result produces `evaluator-error`, `unrunnable: infrastructure`, and a reason of `evaluator-early-exit`, `missing-trusted-result`, or `malformed-trusted-result:<detail>`; exceeding the execution budget produces the same classification with reason `evaluator-timeout` or `evaluator-log-limit`. Missing signatures never compare equal and never become digest candidates.

The violation identity contains only those four components. The final stable failure signature adds `oneMinimalSpecDigest`. Timestamps, stack traces, arbitrary messages, object-key order, and raw logs are excluded.

Evidence records the target revision, module registration ID, `clean` or defect ID, target artifact, evaluator image ID, pinned base image, target and every first-party tarball and exports digest, consumer lockfile, target patch, runner, harness, plan builder, action adapter, comparison direct materializer, trusted invariant evaluator, result serializer, fixture catalog and materializer, invariant catalog, operator catalog, canonicalizer, and replay information.

The Phase 2 trusted result schema is `bug-dreamer/trusted-result/v1`. It contains exactly `schemaVersion`, `specDigest`, `planDigest`, `targetArtifactDigest`, `invariantRegistrationId`, `evaluatorStatus`, `execution`, `observedKind`, allow-listed `observedFields`, `violationIdentity`, and `payloadDigest`. The payload digest uses the `bug-dreamer/trusted-result/v1\0` domain prefix over the JCS bytes of every field except `payloadDigest`.

The evaluator atomically writes at most one regular file, `/result/result.json`, into a fresh per-run result mount. The host accepts no other result filename and validates the raw JSON, strict fields, spec and plan digests, target and invariant bindings, observed-field allow-list, violation identity, and payload digest after the container exits. Stdout, stderr, marker-shaped seed values, and other product files are never inputs to this validation. A missing file, malformed JSON, duplicate key, wrong digest, early exit, evaluator exception, or serializer exception yields `evaluator-error` and `unrunnable: infrastructure` without a violation identity.

Every trust evaluation runs under a host-enforced execution budget: a 30000 ms wall-clock limit and a 1048576-byte cap per stdout and stderr stream. The runner names each container, force-removes it when the budget is exceeded, and records `timedOut`, `outputTruncated`, and the observed byte count per stream; evidence stores at most 4096 raw bytes per stream. The budget values are part of the evaluation contract key, and exceeding the budget is never a candidate failure.

The evaluation contract key contains all of those immutable inputs, including target revision, module registration, and clean or defect identity. The OCI image label records the full key and component digests. Human-readable tags may abbreviate it, but execution and evidence use the full key and image ID.

## Reproduction and minimization

A public candidate must show the same product behavior and violation identity in five of five runs. Each run uses a new container and tmpfs with no shared writable volume. Seed, replay path, virtual-clock origin, random policy, platform, OS, architecture, target artifact, and evaluator digests are fixed.

Time operators use registered virtual-clock advances. Asynchronous ordering uses deferred completion release, not host sleep or wall-clock timing.

Independent reproduction uses a separate session, rebuilds the evaluator for the same evaluation contract key, and replays the same canonical spec and path. Evidence records an original session ID, a different reproducer session ID, and a separate build attestation. A matching content-addressed image ID is allowed and records `matched`; a different image ID for the same key records `diverging-build` and blocks publication.

Reduction uses a fixed order and removes dependency closures for actors, actions, bindings, paired schedule controls, faults, and fixtures until a fixed point. Invalid reduced specs do not count as failed removal attempts. The result is called 1-minimal only with respect to the registered reduction rules and must pass another five-of-five replay.

## Publication gate

`confirmed-counterexample` is derived only when all of the following are true:

```text
accepted and planned and evaluated and completed
and candidate-failure
and consistent 5/5
and independent reproduction is matched
and public-export
and independent oracle
and one-minimal
and human verdict is real-bug-worth-fixing or real-bug-not-worth-fixing
and known defect implies per-patch F-to-P
```

Internal findings and legacy reports remain visible but separate. Existing nightmares are never deleted merely because they fail a new gate. Reports label future incident narratives `Hypothetical` and classify impact as `Observed`, `Inferred`, or `Speculative`.

## Historical audit and replay

The v0.2 path universe is partitioned into `frozenRuntimeInputs`, `frozenHistoricalOutputs`, and `baselineSnapshotOnly`. The sets are disjoint and cover the complete baseline tree. The first set covers legacy entrypoint import closure, Docker build context, module registration, executable benchmark scenarios and reproduction inputs. The second covers benchmark registration, invariant and prompt records, evidence, measured results, digests, and nightmares. The final set preserves the rest of the baseline tree without preventing v0.3-only dependency and documentation changes from entering the current worktree.

The root `package.json` and `pnpm-lock.yaml` are baseline snapshots. Only the engine, package manager, legacy runner scripts, lockfile format, lockfile settings, and any dependency projection actually consumed by v0.2 are frozen. v0.3-only dependency and lockfile sections may change only while they remain outside the legacy import and Docker build closures.

The history validator rejects changes or deletion in the first two sets, additions or removals in the legacy import or Docker input closure, and unregistered additions in reserved legacy namespaces. v0.3-only paths are allowed only when they remain outside the legacy closure.

The pinned target archive input is captured as Git tree entries from the target revision. The validator reconstructs the null-delimited `git ls-tree` representation for every registered module and compares both its path count and SHA-256 digest. The capture file is itself anchored by the history manifest.

Each of the seven audit records contains its original command, scenario path and SHA-256 hash, one or more primary evidence references, every result axis, a static hypothesis that is not a verdict, and any data gap. It contains the recorded image ID when present and an explicit data gap when the ID is missing. Structured independent-reproduction evidence is linked when it exists.

Image preservation is exactly one of the following, using the first matching row:

| Preservation state | Required evidence |
| --- | --- |
| `exact-replayable` | original evidence, scenario hash, image ID, and a verified exact archive whose hash and restored image identity match |
| `best-effort-rebuilt` | no exact archive, but original evidence, scenario hash, image ID, and a verified rebuilt archive from pinned source and harness inputs |
| `evidence-preserved` | no exact or rebuilt archive, but original evidence, scenario hash, and image ID remain |
| `unrecoverable` | original evidence, scenario hash, or image ID is missing |

An archive with a digest, restored image ID, OCI digest, or platform mismatch is not a preservation artifact. The mismatch is retained as evidence and the next applicable preservation state is selected. Replay result is separately one of `not-attempted`, `pass`, `mismatch`, `unavailable`, or `error`.

An exact replay first validates the frozen runtime, scenario, evidence, and image ledger, then uses the recorded image ID directly. It never resolves or temporarily replaces a mutable tag. A verified archive records locator, archive digest and byte length, restored image ID, OCI digest, platform, and a hashed verification receipt. The receipt records the verification command, time, digest and identity checks, target revision, dependency reference, baseline commit, and path manifest anchor. A rebuilt receipt additionally records the pinned rebuild inputs. A rebuilt image is labeled best-effort, runs by its separately recorded restored image ID, and is never presented as exact.

`history --replay-available` inspects every distinct recorded image ID or registered best-effort restored image ID and runs every registered replay case for each available image. Each result identifies the historical image, executed image, exact or rebuilt mode, scenario, observed outcome, and signature match. A locally available replay requires a hashed result reference whose normalized case results match the live replay and whose aggregate status matches the ledger. A recorded and supported `mismatch` or unavailable image gap is an audit outcome, not by itself a validation failure. Failing to attempt an available image, losing a required result reference, or producing a result that does not identify the image and scenario is a validation failure.

## Validator CLI

All validator commands run from the repository root on Node.js 24.

```text
node scripts/validate-v03.mjs history [--replay-available]
node scripts/validate-v03.mjs contracts
node scripts/validate-v03.mjs spec
node scripts/validate-v03.mjs trust
node scripts/validate-v03.mjs operators
node scripts/validate-v03.mjs replay
node scripts/validate-v03.mjs benchmark
node scripts/validate-v03.mjs evidence
node scripts/validate-v03.mjs reports
node scripts/validate-v03.mjs all
```

No other subcommand or option is valid. Exit 0 means every owned positive and negative fixture passed. Exit 1 means the command was valid but a contract check failed. Exit 2 means invalid usage or an unknown command.

`history` is implemented in Phase 0, `contracts` in Phase 1, and `spec` plus `trust` in Phase 2. A later subcommand must fail as not implemented until its owning phase provides the contract fixtures; it cannot return success as a placeholder. `all` becomes successful only after every phase-owned validator exists.
