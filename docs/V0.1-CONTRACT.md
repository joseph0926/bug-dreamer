# v0.1 Execution and Evidence Contract

## Purpose

This document defines what an execution result means, what evidence a reported failure must carry, and what counts as reproduction in v0.1. It does not define a reusable schema or a multi-runner abstraction.

## Target

- Project: [`joseph0926/firsttx`](https://github.com/joseph0926/firsttx)
- Revision: `f624b09f148c3368a51807f48d3237db20cef9c6`
- Module: `packages/tx`
- Runtime: Node.js 24
- Package manager: pnpm 11.17.0 through Corepack
- Test runner: Vitest
- Included behavior: imperative transaction state, retries, total timeout handling, external aborts, and reverse-order compensation
- Excluded behavior: React hooks, DevTools behavior, and View Transition presentation

The existing [`transaction.test.ts`](https://github.com/joseph0926/firsttx/blob/f624b09f148c3368a51807f48d3237db20cef9c6/packages/tx/tests/transaction.test.ts) and [`retry.test.ts`](https://github.com/joseph0926/firsttx/blob/f624b09f148c3368a51807f48d3237db20cef9c6/packages/tx/tests/retry.test.ts) files are reference material for product behavior. The target package defines `pnpm --filter @firsttx/tx test:run` and `pnpm --filter @firsttx/tx typecheck` as its narrow verification commands. Bug Dreamer may invoke them only through the isolation runner. Generated scenarios must not edit the target project outside the disposable environment.

## Execution phases

The runner records an explicit marker whenever it enters a phase.

| Phase | Meaning | If it cannot complete |
| --- | --- | --- |
| P1 Environment | Create the disposable environment, restore the exact revision and dependencies, and apply network and resource limits. | Unrunnable: infrastructure |
| P2 Test preparation | Load or compile the generated test and prepare its fixtures. | Unrunnable: test definition |
| P3 Target execution | Execute the selected `packages/tx` behavior. | Candidate failure only when the error can be attributed to the target behavior |
| P4 Oracle evaluation | Compare the observed result with the recorded expectation. | Candidate failure when the expectation is violated |

An ambiguous error is unrunnable. A nonzero exit code alone never proves a product failure.

## Outcome semantics

### Pass

P4 completes and the oracle is satisfied. The only permitted claim is that this scenario did not expose a bug. A pass is not evidence that the module has no bug and never appears in a nightmare report.

### Candidate failure

P4 completes and the oracle is violated, or P3 ends abnormally in a way that can be attributed to the selected target behavior. The permitted claim is that the implementation differed from a recorded product expectation. Only a human can decide whether that difference is a real bug and worth fixing.

### Unrunnable

The run cannot produce a valid product observation. The record uses one of two reasons:

- `infrastructure`: environment creation, dependency restoration, isolation, or runner failure
- `test-definition`: generated test loading, compilation, fixtures, framework use, or oracle control failure

A harness-enforced timeout or resource limit is `unrunnable: infrastructure` because P4 did not complete. A timeout value returned or thrown by the target and evaluated by P4 is ordinary target behavior and may pass or fail its oracle.

Blocked access to a network service, secret, credential, or personal configuration makes the scenario unrunnable. It is never evidence of a product failure.

## Oracle basis

Every candidate failure cites an expectation source that exists independently of the generated scenario. Accepted basis types are:

- `documentation`: an explicit behavior statement in project documentation
- `existing-test`: an expectation in the target project's existing tests
- `public-type`: a public type or function contract
- `declared-invariant`: an invariant explicitly maintained by the target module

An assumption without one of these sources is not eligible for the nightmare report. Reading an implementation and inventing the desired behavior from it does not create an independent oracle.

When a known-good example exists for the same oracle, the generated test includes it as a control. If the control fails, the run is `unrunnable: test-definition`. When no suitable control exists, the evidence records why.

## Evidence fields

The notation below illustrates field names and meaning. v0.1 does not require a schema validator or commit to a serialization format.

```yaml
evidence:
  scenario_id:
  target:
    project:
    project_revision:
    module:
  environment:
    isolation:
    image_or_os:
    runtime:
    dependencies_ref:
    limits:
      network: blocked
      allowed_commands:
      timeout:
      memory:
  test:
    test_ref:
    test_hash:
    oracle_basis:
    oracle_basis_ref:
    control_ref:
  reproduction:
    command:
    working_directory:
  inputs:
  expected:
  actual:
  runs:
    attempts:
    failures:
    per_run:
      - phase_reached:
        outcome:
        duration:
        exit_reason:
  classification:
    outcome:
    unrunnable_kind:
    failure_signature:
    rule:
  logs:
    excerpt:
    full_ref:
  human_verdict: unreviewed
```

`classification` is produced from recorded execution facts. Automation must leave `human_verdict` as `unreviewed`. The user may later set it to one of:

- `real-bug-worth-fixing`
- `real-bug-not-worth-fixing`
- `wrong-expectation`
- `undecided`

Both `runs.per_run[].outcome` and `classification.outcome` use `pass`, `candidate-failure`, or `unrunnable`. `unrunnable_kind` is present only for an unrunnable result. `failure_signature` is present only for a candidate failure. `rule` identifies the classification rule applied to the recorded facts.

## Reproduction

A candidate becomes reportable only after the author records three consecutive runs with the same failure signature. Intermittent failures are retained as evidence but are not reported in v0.1.

A third party reproduces the failure when all of the following hold:

1. They use only the recorded evidence and no unrecorded secret, setup, or verbal instruction.
2. They restore the recorded project revision and equivalent isolated environment.
3. They run the recorded command unchanged. The command invokes the isolation runner rather than the target test command directly on the host.
4. They observe the same failure signature at least once.

The same failure signature means the same oracle is violated in the same direction, or the same error type arises from the same target code path. Logs, durations, unrelated warnings, and generated identifiers do not need to be byte-for-byte identical.

An unrunnable third-party attempt is inconclusive. It does not reproduce or refute the failure and should trigger a correction to the environment evidence when the record is incomplete.

## Nightmare report

Reports are written to `nightmares/YYYY-MM-DD.md`. Multiple reportable nightmares from the same day are appended to one file and ordered by estimated reachability and impact. Passing and unrunnable results stay in the evidence records and never appear in this report.

The timeline is fiction, reproduction facts are observed evidence, and impact is an estimate. These labels must remain explicit.

```markdown
# Nightmares — YYYY-MM-DD

Target: <project> @ <revision> — <module>
Run: manual, isolated

## 1. <short title>

### Incident timeline (fiction, future-dated)

- YYYY-MM-DD HH:MM — <first symptom>
- YYYY-MM-DD HH:MM — <impact discovered>

### Reproduction (fact)

<single copyable isolation-runner command>

Observed: failed <M>/<N> runs. Evidence: <evidence reference>

### Failing test (fact)

- Test: <test reference>
- Expectation basis: <basis type> — <source reference>
- Expected: <expected result>
- Actual: <observed result>
- Failure signature: <signature>

### Relevant code path (fact)

<file and line chain through the target module>

### Impact note (estimate)

<who can reach this state, what breaks, and why the impact matters>

### Human verdict

- [ ] Real bug, worth fixing
- [ ] Real bug, not worth fixing
- [ ] Expectation was wrong
- [ ] Undecided

Notes:
```

The ranking is an estimate, not execution evidence. A `wrong-expectation` verdict removes the candidate from the active nightmare report while preserving the evidence record and verdict.

## Deferred decisions

The isolation technology, runner CLI, exact command allowlist, time and memory limits, dependency snapshot representation, and framework-specific signature extraction remain undecided until the runner is selected. v0.1 must not introduce a shared package, formal schema validator, flaky-test statistics engine, automated oracle judge, reachability proof, scoring model, dashboard, or multi-runner abstraction.
